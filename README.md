# Учебный интернет-магазин «Магнит»

Бэкенд на Java 21, Spring Boot 3.3.5, Spring Security, PostgreSQL, Liquibase и JWT.
Каталог → корзина → оформление заказа → обработка менеджером → история покупок.


## Запуск

Нужны JDK 21, Maven 3.6.3+ и PostgreSQL. Выполняйте команды из папки `untitled`.

1. Создайте базу `online_shop_magnit` (UTF-8). Для поиска русских названий без учёта регистра используйте локаль с поддержкой кириллицы.
   Например, в PostgreSQL 16 при наличии ICU:
   ```sql
   CREATE DATABASE online_shop_magnit
       TEMPLATE template0 ENCODING 'UTF8'
       LOCALE_PROVIDER icu ICU_LOCALE 'ru-RU';
   ```
   Если база уже существует, создавать её повторно не нужно. Локаль `C` не обеспечивает смену регистра кириллицы.
2. В PowerShell задайте параметры подключения и секрет:
   ```powershell
   $env:DB_URL = 'jdbc:postgresql://localhost:5433/online_shop_magnit'
   $env:DB_USERNAME = 'postgres'
   $env:DB_PASSWORD = '<пароль вашей PostgreSQL>'
   $secretBytes = New-Object byte[] 48
   $rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
   $rng.GetBytes($secretBytes)
   $rng.Dispose()
   $env:JWT_SECRET = [Convert]::ToBase64String($secretBytes)
   mvn spring-boot:run
   ```
   Сохраните сгенерированный JWT_SECRET в настройках запуска IDE для последующих запусков: смена секрета делает старые токены недействительными.
   Секрет — строка минимум 32 байта UTF-8. Пароль БД и JWT_SECRET обязательны, общедоступных значений по умолчанию нет.
3. Откройте [Swagger UI](http://localhost:8080/swagger-ui/index.html). Спецификация: [OpenAPI JSON](http://localhost:8080/v3/api-docs).

Миграции применяются автоматически при запуске на каждом окружении. Создаются таблицы, роли, администратор и демонстрационный каталог.

## Начальные данные и вход администратора

- Логин: `admin@gmail.com`.
- Пароль: `zaq123456`.
- Роли: ROLE_ADMIN и ROLE_USER.
- Миграция 010 хранит BCrypt-хэш пароля, а не открытый пароль.
- Миграция 011 создаёт 5 категорий и 15 товаров: по 3 товара в каждой категории.
- Категории: молочные продукты, хлеб и выпечка, напитки, овощи и фрукты, бакалея.

Можно сразу войти на фронтенде либо через POST /api/auth/login в Swagger. В Swagger вставьте полученный token в Authorize без слова Bearer. Регистрация администратора вручную и дополнительный скрипт наполнения больше не нужны.

ID назначает база. Существующие категории и товары сопоставляются по названию; их цены, описания и остатки не изменяются. Если аккаунт admin@gmail.com уже существует, его имя и пароль сохраняются, добавляются необходимые роли. Для существующего аккаунта используйте его прежний пароль.

Повторный запуск не создаёт дубликаты и не сбрасывает изменения: Liquibase записывает выполненные changeset. Удалённые впоследствии демонстрационные товары при перезапуске не восстанавливаются.

Старый файл 008 с фиксированными ID оставлен для истории, но исключён из master changelog. Новые 010 и 011 работают как на чистой базе, так и при уже выполненном старом наполнении. У 009 восстановлен исходный идентификатор changeset, совпадающий с историей существующей базы.

Дальнейшее управление пользователями доступно через GET /api/admin/users, GET /api/admin/roles и PUT /api/admin/users/{id}/roles. Нельзя снять ADMIN у себя или удалить последнего администратора.

## Права

| Возможности | Без входа | USER | MANAGER | ADMIN |
|---|---|---|---|---|

## Контракт API для фронтенда

| Раздел | Основные маршруты |
|---|---|
| Вход и регистрация | POST /api/auth/register, POST /api/auth/login |
| Текущий пользователь | GET /api/users/me |
| Товары | GET /api/products?name=молоко&categoryId=1, GET /api/products/{id} |
| Категории | GET /api/categories?name=молочные, GET /api/categories/{id} |
| Корзина | GET /api/cart, PUT /api/cart/items/{productId}, DELETE /api/cart/items/{productId}, DELETE /api/cart |
| Оформление корзины | POST /api/cart/checkout |
| Прямое оформление | POST /api/orders |
| История покупок | GET /api/orders, GET /api/orders/{id} |
| Отмена покупателем | POST /api/orders/{id}/cancel |
| Менеджер | GET /api/management/orders, PATCH /api/management/orders/{id}/status?status=PAID |
| Администратор | /api/admin/products, /api/admin/categories, /api/admin/orders, /api/admin/users, /api/admin/roles |

Пример товара:
```json
{"name":"Молоко 3,2%, 1 л","description":"Пастеризованное","price":89.90,"stockQuantity":100,"categoryId":1}
```
Пример добавления в корзину: `PUT /api/cart/items/1` с телом `{"quantity":2}`.
PUT задаёт итоговое количество, а не прибавляет его. Корзина хранит до 100 разных товаров, количество позиции — от 1 до 10000.
Она не резервирует товар; цена и остаток проверяются при оформлении.
Пример прямого заказа:
```json
{"items":[{"productId":1,"quantity":2}]}
```

Заказ содержит `id`, `userId`, `createdAt`, `status`, `items`, `total`.
Позиция содержит `productId`, `productName`, `quantity`, `priceAtPurchase`, `subtotal`.
Цена фиксируется при покупке, итог рассчитывается сервером в рублях. Название товара берётся из актуального каталога.
Время создания — локальное время сервера (сохранён исходный формат БД).
Пароли, Hibernate-прокси и обратные ссылки сущностей в ответы не попадают.

Ошибки возвращаются в JSON:
```json
{
  "timestamp":"2026-10-27T12:00:00Z",
  "status":400,
  "message":"Проверьте введённые данные",
  "path":"/api/orders",
  "errors":{"items[0].quantity":"must be greater than or equal to 1"}
}
```
400 — некорректные данные; 401 — требуется вход; 403 — недостаточно прав; 404 — запись не найдена; 409 — конфликт, нехватка товара или недопустимый переход статуса.
Сообщения ограничений в `errors` могут зависеть от локали валидатора.
Чужой заказ возвращает 404, чтобы не раскрывать факт его существования.

Фронтенд передаёт заголовок `Authorization: Bearer <token>`. JWT живёт 24 часа по умолчанию; срок задаётся `JWT_EXPIRATION_MS`.
Для выхода удалите токен на клиенте. Серверного отзыва токенов и refresh token пока нет.
Пароль: 8–72 символа и не более 72 байт UTF-8 (ограничение BCrypt); кириллица поддерживается.

CORS разрешён для `http://localhost:5500`, `http://127.0.0.1:5500`, `http://localhost:5173`.
Другие адреса задаются переменной `CORS_ALLOWED_ORIGINS` через запятую.
Запускайте будущий фронтенд через локальный HTTP-сервер. Для выпадающего списка категорий показывайте name, отправляйте id.
При 401 показывайте форму входа; при 403 — понятную страницу или окно «Недостаточно прав».
Для этого REST API используется JSON-обработчик AccessDeniedHandler; HTML-страницу из требования практической №7 нужно реализовать на фронтенде.

## Правила заказов

- Статусы: NEW → PAID → SHIPPED → DELIVERED.
- Отмена допустима из NEW или PAID; покупатель самостоятельно отменяет только NEW.
- Повторное назначение текущего статуса не списывает и не возвращает остаток повторно.
- CANCELLED и DELIVERED — конечные состояния.
- PAID — учебная отметка сотрудника. Подключения банка, реального списания и возврата денег нет.
- Остатки защищены транзакциями и блокировками строк. При нехватке любого товара весь заказ откатывается.
- При отмене остаток возвращается один раз. Оформление корзины и её очистка выполняются в одной транзакции.
- Прямой POST /api/orders создаёт новый заказ при каждом успешном вызове; не повторяйте его автоматически после сетевого таймаута. Сначала проверьте историю.
- Товар, используемый в заказе или корзине, нельзя удалить: 409. Для остановки продажи установите остаток 0.
- При удалении категории товары сохраняются без категории.

## Проверка и сборка

```powershell
mvn test
mvn package
java -jar target/online-shop-1.0-SNAPSHOT.jar
```

Тесты используют отдельную H2 в памяти, выполняют Liquibase и проверяют схему через Hibernate.
Только в тестовом changelog TEXT преобразуется в VARCHAR(10000), поскольку Liquibase отображает TEXT в CLOB для H2.
Рабочие миграции при этом не меняются. Дополнительно сценарии проверены на PostgreSQL 16 в отдельном временном кластере.

Интеграционные проверки покрывают регистрацию и BCrypt, Unicode-пароли, JWT, разграничение прав, валидацию,
CRUD и поиск, сериализацию ответов, доступ к чужим заказам, цены и остатки, откат, отмену, корзину, Swagger, CORS
и конкурентные покупки, оформление корзины и изменение ролей.

Для повторения PostgreSQL-тестов используйте только отдельную локальную базу `shop_test` или `shop_test_<суффикс>`.
Тесты очищают её таблицы перед каждым сценарием; URL другой базы отвергается до очистки.
Пример для заранее созданной тестовой базы с ICU ru-RU:
```powershell
mvn test '-Dspring.datasource.url=jdbc:postgresql://127.0.0.1:55439/shop_test_ru' `
  '-Dspring.datasource.username=postgres' '-Dspring.datasource.password=<тестовый пароль>' `
  '-Dspring.datasource.driver-class-name=org.postgresql.Driver' `
  '-Dspring.liquibase.change-log=classpath:db/changelog/db.changelog-master.yaml'
```
